实测（两轮，均已回退）**：第一轮按「12 点 MDCT + 3 窗口 + 带内按窗重排 + 单一 Huffman 表 + `scalefac_compress=0` + `subblock_gain=0`」实现后，自有解码器与 Chromium `decodeAudioData` 都解出宽带噪声。第二轮定位到根因：`MeasureShort` 把 `LongTables` 的**数组下标**当成 `table_select` 的表号写进边信息（下标 20 实际是表 23），导致声明位数比实际写入少约 25%，解码端读串；修好后码流结构完全合法（静音帧静音、正弦能解出正弦）。但质量仍不达标：瞬态码流 192 kbps 往返 12.4 dB，**低于纯长块的 22.1 dB**——原因是本实现放弃了短块的四分区 slen + `subblock_gain` 逐带整形，576 条短块谱线共用一个量化步长，逐线精度远低于长块的 21 带缩放因子。结论：闸门③（逐带缩放因子 + `subblock_gain`）是短块"有效"的必要条件，不做它短块只会更差。可复用的排查资产：①`NL_MP3_BITS_CHECK` 那种「声明位数 vs 实际写入位数」自检（一开就能抓出 table/码字不一致）；②VS Code 内嵌 Chromium 的 `decodeAudioData` 黑盒验证（本地无 ffmpeg 亦可判互通）；③静音帧结构自检（先验边信息、再验谱线）。160 真机已装 .NET 10 SDK 可跑全量测试。**2026-10-27 第三轮（同样已回退，但把约定钉死了）**：用「解码端 `Mp3Layer3Dsp.Imdct` 当综合端，扫分析端参数看重建误差」的 TDAC
