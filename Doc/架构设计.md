# NewLife.Audio 架构设计

> 版本：v1.6 | 日期：2026-10-26 | [← 返回 README](../README.zh-CN.md) | [文档索引](README.md)

这份文档写给"懂图片编解码、不懂音频"的开发者：先建立直觉，再看清一个完整音频库应该由哪些层组成，最后对照出我们真实的完成度与缺口。算法细节不在这里展开，见各模块设计文档。

> 本文的"真实深度"评级来自 2026-10-26 的源码逐文件核对，不是功能清单的自评结果。凡与清单不一致处，以本文证据为准，并在第 10 章给出回流建议。

### 0.2 第 2 章：七层能力栈逐层翻译

| 层 | 大白话 | 图像里的对应物 | 缺了会怎样 | 我们的状态 |
|---|---|---|---|---|
| L0 采样数据模型 | 一张"格式说明单"：每秒采样多少次、几声道、16 位整数还是 32 位浮点 | 宽×高×色深×通道 | 各模块自己猜格式，类型对不上就出噪音且**不报错** | ★★★，显式 SampleFormat + 平面/交错 + 有效位/声道掩码 + AudioFrame |
| L1 容器 | 文件外壳：文件头、标题封面等元数据、能拖动的索引 | PNG/JPEG 文件格式 | 只有裸数据，播放器打不开、拖不动 | ★★★，WAV/MP3/MP4/FLAC/Ogg/AIFF 可读写，CAF 只读 |
| L2 编解码 | 压缩与解压：PCM ↔ 码流 | zlib / JPEG 压缩 | 只能存巨大 WAV（1 分钟 CD 音质约 10 MB） | 长板（Opus 托管实现仍是缺口） |
| L3 设备 I/O | 与操作系统声卡打交道：PCM 送进喇叭、麦克风取回 PCM | 显卡/显示器驱动 | 库只能算，**不能听不能说** | Windows 已补齐 WinMM + WASAPI；ASIO 与跨平台仍缺 |
| L4 DSP | 通用处理：音量、重采样、混音、EQ、频谱 | 滤镜（模糊/锐化/调色） | 只能原样播放 | 齐全，含线性/加窗 Sinc 与 EBU R128 |
| L5 语音前处理 | 通话四件事：VAD 有无话音、AEC 消回声、AGC 稳音量、NS 降噪 | 会议软件里的降噪 | 通话场景不可用 | 有，属"基础可用"级 |
| L6 TTS/ASR | 文字→声音、声音→文字 | OCR / 图像描述 | 做不了播报类应用 | TTS 桌面/云端/离线包可用，移动端无；ASR Windows + 离线包可用，移动端无 |
| L7 工程化 | AOT、多框架、移动端打包、本地化 | 能否上架应用商店 | "能跑 demo、上不了生产" | 最扎实 |

两点补充：

- **编码比解码难一个量级**：解码是确定性逆运算，做对即满分；编码要自己决定扔哪些"听不出来"的信息，依据是心理声学掩蔽（响的声音盖住邻近弱声）。砍得准 = 低码率好音质，砍不准 = 发闷有毛刺——这是 MP3 编码仍需补短块、Opus 托管 CELT/SILK 尚未完成的根因。
- **L0 值得单独一层**：所有层之间交换的都是"这段 PCM"，格式说明单错一格，整条链都错，且往往以噪音而非异常的形式暴露。

### 0.3 第 3 章怎么读

评级四档：★★★ 能用（有测试或外部工具验证）｜★★ 能用但有局限｜★ 骨架（方法体空或占位）｜— 不存在。

**空壳的成因（历史教训）**：骨架期先写齐类型、接口、参数（编译能过、IDE 里看着像完成），方法体留空。后果很隐蔽——调用不报错但没声音；设备枚举返回硬编码条目，拔了还在；`.NET 8/10` 默认落到 `FallbackDriver` + `NullRecorder`，录音"成功"却拿到空数据。所以本文坚持**按源码行为评级，不按注释自评**。

**结论只记三组**：

- **真能打**：G.711/ADPCM/G.722/G.726、MP3 解码、AAC-LC 编解码、FLAC、Vorbis 解码、DSP、容器读写与文件门面、SAPI TTS、AOT 与打包。
- **半成品**：MP3 编码（短块未做）、HE-AAC、Vorbis 编码（长块基线）、Opus（托管 CELT/SILK 未做）、语音前处理（与 WebRTC APM 有工程化差距）。
- **仍缺**：ASIO、Linux/macOS/Android/iOS 设备后端、移动端 TTS/ASR、托管 Opus。

**dB 标尺**（读第 3 章数值用）：>60 基本听不出差异；40 左右有细微瑕疵但可用；30 明显但仍能听；20 以下明显失真；15 即"一听就坏"。对照：AAC 编码 35.9 dB 及格偏上、Vorbis 解码 85~89 dB 几乎完美、Vorbis 编码 31 dB 一般。

### 0.4 第 4 章：G1~G9 一句话版

排序原则：缺了它用户会直接说"这库不能用"的排 P0；影响成品听感/体验的排 P1；有明确需求再做的排 P2。

| 编号 | 大白话 | 当前影响 | 补法 / 状态 |
|---|---|---|---|
| G1 P0 | 原：只有 WinMM 一条路真出声，WASAPI/ASIO 是空壳，其他平台为零；现：Windows WinMM + WASAPI 已补齐，ASIO 与跨平台后端仍缺 | 非 Windows 平台仍无设备后端，跨平台承诺不完整 | 先改运行时选驱动（已完成），再补 WASAPI（已完成），再各平台原生后端 |
| G2 P0 | 原：有零件没成品；现：`AudioFile` 门面、Probe、标签、原子保存与 MP3/ADTS/WAV/Ogg Opus 帧级复制已落地 | 主路径已闭环，`AudioFile` 提供清晰路径 | 新增 `AudioFile` 门面 + 重写 WAV 解析 + 补写入器（已完成） |
| G3 P0 | Opus 靠 ffmpeg 子进程，不是自己会 | 没装 ffmpeg 的机器（手机、容器、干净 Windows）等于不支持 | 托管 CELT/SILK 分步推进；降级链为平台原生 → ffmpeg → 明确报不支持 |
| G4 P1 | 原：MP3 能编码但音质差；现：心理声学、M/S、VBR/ABR、Xing、编码比特池、坏帧错误隐藏与 CRC 已补齐，门禁口径 13.8 dB，短块待排期 | 短块缺失导致瞬态（打击乐/爆破音）偏糊 | 短块与窗口切换（CODEC-6d）；质量门禁守回归 |
| G5 P0 | 原：格式说明单太薄；现：显式 `SampleFormat`、平面标记、有效位、声道掩码与 `AudioFrame` 已全部落地 | 已闭环 | 显式 `SampleFormat` + 平面标记 + 边界转换（已完成） |
| G6 P1 | 原：TTS 缺 Android/iOS 系统引擎，输出只有 WAV；现：MP3/FLAC 已接入，移动端仍缺 | 移动端 TTS 是高频场景，目前空白 | 随平台 TFM 各补约 100~200 行封装 |
| G7 P1 | 原：重采样只有线性，缺响度归一化与混响；现：线性 + 加窗 Sinc 与 EBU R128 已落地，混响未做 | 重采样/响度已解决，混响仍缺 | 多相 Sinc 重采样 → EBU R128（已完成）；混响按需求再做 |
| G8 P2 | 原：ASR 零实现；现：接口、Windows 系统识别、流式端点与 sherpa 离线包已落地，移动端缺 | 移动端识别仍空白 | `ISpeechRecognizer` + 系统能力或可选包（已完成主体） |
| G9 P2 | 原：AMR/G.729/ALAC/AC-3/AIFF/CAF 未做；现：AIFF 双向、CAF 读取已补，AMR/G.729/ALAC/AC-3 未做 | AMR/G.729/ALAC/AC-3 仍缺，按需求再做 | 有需求再做；AIFF/CAF 随 G2 一起补（已完成） |

第 4 章末尾"文档与实现偏差"表的真正风险不是偏差本身，而是**让规划建立在错的基线上**（以为设备 I/O 已完成 → 排期去做 Opus → 交付时才发现没声音）。

### 0.5 第 5 章：六个关键动机

这一章是写给实现者的施工图（目标接口 + 设计决策），读的时候抓动机即可：

| 设计决策 | 为什么要这样 |
|---|---|
| 运行时选驱动（`OperatingSystem.IsWindows()`）而非编译期 `#if WINDOWS` | .NET 一次编译到处跑，宏在编译期就把平台钉死；运行时判断是消掉"假设备"的最低成本手段 |
| 能力描述而非布尔值 | 只说"支持"不够，还要给出支持的采样率/格式与最小缓冲，否则开流时格式打架 |
| 推 / 拉双模型 | 推 = 应用主动 `Write`（简单，现有）；拉 = 声卡线程驱动（低延迟必须，回调内零分配、零锁、零日志） |
| `Open → ReadPcm → 编辑 → WritePcm/SaveAs` 门面 | Probe 按"魔术字节 > 容器解析 > 扩展名"认格式；remux 只换外壳不重编码；原子保存写临时文件再替换，写坏不毁原文件 |
| 显式采样格式（5.4） | 全库最核心的类型，也是 WASAPI 的前置。平面格式 = 各声道分开存，交错 = LRLRLR；旧代码保持可用，32 位默认按 Int32、浮点需 `IsFloat=true` |
| 质量门禁"自测自解不算通过"（5.9） | 自己编自己解，两边错误可能互相抵消，必须有第二个实现或外部工具对照 |

DSP/语音前处理还有三条容易忽略的：声明延迟与尾部样本（否则切歌、拼接掉样本）、参数平滑（否则调音量出现 zipper noise）、AEC 必须拿"喇叭正在放什么"当参考输入（否则分不清回声与人声）。

### 0.6 第 6~9 章摘要

- **第 6 章 三级降级**：纯托管 → 操作系统能力 → P/Invoke；子进程只做兜底。主包一旦 P/Invoke，无原生库的机器会直接 `DllNotFoundException`；子进程有环境依赖与启动开销，也做不到流式低延迟。
- **第 7 章 平台矩阵**：编解码/DSP 满绿是因为与操作系统无关（纯托管）；设备 I/O 的 Windows 列已补齐 WinMM + WASAPI，其余平台仍红。这张表是第 3 章的浓缩版。
- **第 8 章 移动端**：`TFM` 是目标框架，`workload` 是编译该框架所需工具链。无条件写进 `TargetFrameworks` 会让没装 workload 的机器 `dotnet build` 直接失败，故用 `EnableMobile` 开关；iOS 只能 macOS 编译，发版链路必须 macOS。方案 A（主库条件多目标）优于 B，因为用户只装一个包、平台代码写进主库最自然。
- **第 9 章 路线图**：三阶段 = 先能用 → 再好用 → 再高质量。阶段一验收即"Windows 上真能出声、真能录音，文件能打开→改→另存"；阶段二把同一套能力搬到 Linux/macOS/Android/iOS；阶段三才做 Opus、MP3 音质、高档 DSP。顺序依据：G5 采样格式是 WASAPI 前置，WASAPI 是 Windows 唯一能低延迟与录系统声音的路径，文件门面是用户最容易感知的入口。

### 0.7 只记三句话

1. 算法层是真好（纯托管编解码 + AOT 打包）；Windows 设备 I/O 已补齐 WinMM + WASAPI（含 loopback、热插拔与设备丢失重连），ASIO 与跨平台后端仍是缺口。
2. 阶段一（Windows 真能听能说 + 文件一条龙）已完成；阶段二是 Linux/macOS/Android/iOS 设备后端与移动端 TTS/ASR。
3. Opus 托管编解码、MP3 短块与移动端能力是剩余主线。

## 1. 先建立直觉：图像 ↔ 音频对照

| 概念 | 图像 | 音频 | 本库对应类型 |
|---|---|---|---|
| 基本单位 | 像素 | 采样点（sample） | `Int16` / `Single` |
| 空间精度 | 分辨率（宽 × 高） | 采样率（每秒采样数） | `AudioFormat.SampleRate` |
| 单点精度 | 色深 8/16 bit | 位深 8/16/24/32 bit | `AudioFormat.BitsPerSample` |
| 通道 | RGB / RGBA | 单声道 / 立体声 / 5.1 | `AudioFormat.Channels` |
| 内存中的原始数据 | 位图 | PCM | `IPacket` |
| 文件容器 | PNG / JPEG 文件 | WAV / MP3 / M4A / OGG | `IAudioContainerReader` / `IAudioContainerWriter` |
| 无损压缩 | zlib / PNG | FLAC | `FlacCodec` |
| 有损压缩 | JPEG / WebP | MP3 / AAC / Opus / Vorbis | `Mp3Codec` / `AacCodec` / `OpusCodec` |
| 变换 | DCT（8×8 块） | MDCT（长窗 + 重叠相加） | `IMDCT` 相关实现 |
| 后处理 | 锐化、降噪、滤镜 | EQ、压缩器、混响、重采样 | `IAudioProcessor` 链 |
| 最终呈现 | 屏幕 | 声卡 | `IAudioPlayer` |

**三个关键差异**，决定了音频库的架构与图片库完全不同：

1. **音频是流，不是一张图**。1 秒 44.1 kHz 立体声 = 88200 个采样点，无法整块处理，所有接口必须支持"边收边处理、分块进出"（本库用 `IPacket` + 帧迭代）。
2. **有实时约束**。播放和录音对延迟与卡顿极其敏感，编解码和 DSP 的耗时直接决定能不能用（本库用帧级/块级 API + `IsStateful` 表示有状态流式编解码器）。
3. **有损压缩依据的是听觉心理模型**（掩蔽效应），不是纯粹的数学逼近。这就是为什么**编码器比解码器难一个量级**：解码是确定性的逆运算，编码要在"听不出来"和"码率"之间做取舍。本库 MP3 解码稳定、编码音质不达标，根因就在这里（见 G4）。

## 2. 音频库的标准能力栈

```
                     ┌──────────── 应用场景 ────────────┐
                     │ 播放器 录音 对讲 直播 播报 识别  │
                     └───────────────┬─────────────────┘
L6 语音合成/识别  ──→ 文本 ⇄ PCM      │
L5 语音前处理      ──→ VAD AEC AGC NS ─┤
L4 DSP            ──→ 重采样 滤波 混音 ┤
L3 设备 I/O        ──→ 播放 ⇄ 录音 ────┤
L2 编解码          ──→ PCM ⇄ 码流 ─────┤
L1 容器            ──→ 文件/流 ⇄ 码流  ┤
L0 采样数据模型     ──→ PCM 格式描述 ───┘
```

| 层 | 解决什么问题 | 缺了这一层会怎样 | 业界代表 |
|---|---|---|---|
| **L0 采样数据模型** | 统一描述"这段数据是什么格式的 PCM" | 每个模块各自猜格式，接口无法互通 | NAudio `WaveFormat`、FFmpeg `AVSampleFormat` |
| **L1 容器** | 把码流连同元数据装进文件/网络流，支持随机定位 | 只能处理裸码流，用户打不开、拖不动进度 | libsndfile、FFmpeg avformat |
| **L2 编解码** | PCM ↔ 压缩码流 | 只能存巨大的 WAV，无法传输与存储 | FFmpeg avcodec、Opus、LAME |
| **L3 设备 I/O** | 与操作系统声卡打交道 | 库只能算、不能听不能说 | PortAudio、WASAPI、CoreAudio、AAudio |
| **L4 DSP** | 改音量、改采样率、加效果、看频谱 | 只能原样播放，做不了产品级处理 | SoX、WebRTC APM、SpeexDSP |
| **L5 语音前处理** | 让实时通话听得清（回声、噪声、音量、静音） | 通话场景不可用，是 .NET 生态的空白点 | WebRTC APM、SpeexDSP |
| **L6 语音合成/识别** | 文本 ↔ 声音 | 做不了播报类 IoT 应用 | SAPI、Azure TTS、sherpa-onnx |
| **L7 工程化** | AOT、裁剪、多框架、移动端、线程模型、本地化 | 库"能跑 demo、上不了生产" | —— |

**一条数据通路记牢，后面所有讨论都围绕它：**

```
文件/网络 ──L1解封装──→ 压缩码流 ──L2解码──→ PCM ──L4/L5处理──→ L3播放
麦克风 ──L3采集──→ PCM ──L5前处理──→ PCM ──L2编码──→ 码流 ──L1封装──→ 文件/网络
文本 ──L6合成──→ PCM ──L3播放 或 封装成文件
PCM ──L6识别──→ 文本
```

## 4. 差距清单

按"对用户实际价值"排序，每条给：现象 → 危害 → 建议路线 → 代价。具体目标架构、接口形态与验收口径见第 5 章，差距与需求项的对应见 5.10。

> 以下保留开工前的差距分析作为决策依据；每条新增"现状（2026-10-26）"标注，实际完成状态以[功能模块清单](功能模块清单.md)为准。

### P0：不补就不算一个完整音频库

#### G1 设备 I/O 只有一条真实路径

- **现状（2026-10-26）**：Windows 侧已补齐 WinMM + WASAPI（真实枚举、共享模式播放/采集、loopback、事件回调低延迟、设备丢失重连、热插拔观察）；ASIO 明确不支持；Linux/macOS/Android/iOS 仍无实现。
- **现象**：全库只有 WinMM（WaveOut/WaveIn）真正调用系统 API。WASAPI 播放器 `Write` 为空、设备枚举是硬编码两条；ASIO 没有任何原生调用；Linux/macOS/Android/iOS 无实现；`.NET 8/10` 默认还会落到假驱动，录音直接静默失败。
- **危害**：
  - 在 .NET 8/10（也就是 AudioStudio 和绝大多数新项目）上，"枚举设备"看到的名字是假的，"录音"拿到的是空数据——用户会认为库坏了。
  - 跨平台承诺（README 写着 Windows \| Linux \| macOS \| Android \| iOS）在设备 I/O 上目前不成立。
- **建议路线**（三层推进，每层都保持纯托管 + OS API，不引第三方音频包）：
  1. **先修"选择逻辑"**：驱动选择改成运行时判断（`OperatingSystem.IsWindows()`），而不是编译期 `WINDOWS` 宏；`FallbackDriver` 在非 Windows 明确返回"不支持"而不是假装成功。这是半天工作量，能立刻消除"假设备"。
  2. **Windows 补齐**：WASAPI 走真正的 `IMMDeviceEnumerator` + `IAudioClient`（共享模式播放/采集 + loopback）；ASIO 用现有注册表检测 + 动态加载 `*.dll` 的 `ASIO*` 导出函数。ASIO 可以放后面，WASAPI 必须做——它是 Windows 上唯一能做低延迟和回路录制的路径。
  3. **各平台原生后端**：Linux 用 ALSA（`libasound`，最底层、无守护进程依赖）→ 需要时再加 PulseAudio；macOS 用 AudioToolbox/AudioQueue；Android 用 AAudio（API 26+）/AudioTrack+AudioRecord；iOS 用 AVAudioEngine/AVAudioSession。移动端两个必须放在平台 TFM 里（见第 8 章）。
- **代价**：这是全库工作量最大的一块，且每平台都要真机验证。建议先做 Windows WASAPI + Linux ALSA + Android AAudio 三条，覆盖 90% 场景。

#### G2 文件"读 → 改 → 写"闭环不成型

- **现状（2026-10-26）**：`AudioFile` 门面、`AudioProbe`、统一标签、原子保存、MP3/ADTS/WAV 帧级复制与重封装、AIFF/CAF 已落地（Opus 帧复制与流式读取待补）；下表为开工前基线。
- **诉求**：pcm/wav/mp3/opus/aac/ogg 都要能读写和修改。按"标签 + 无损内容操作"的口径逐项对账：

| 格式 | 读 | 写 | 改标签 | 改内容（裁剪/拼接/音量/重采样） |
|---|---|---|---|---|
| WAV | ★★ | ★★ | — | 无（只能自己读帧→改→自己写） |
| MP3 | ★★★ | ★★★ | ✅ ID3v2.4 + ID3v1 | 无现成 API |
| AAC（ADTS/raw/M4A） | ★★★ | ★★★ | M4A 无标签 | 无 |
| OGG（Vorbis/Opus） | ★★ | ★★ | 部分（Opus Tags 已打通，Vorbis 注释需自备头包） | 无 |
| FLAC | ★★ | 仅整段编码 | 无 | 无 |
| 裸 PCM | ★★ 读 | ★★ 写 | — | 无 |

- **现象**：容器层只提供"逐帧读取器 + 逐帧写入器"，没有面向用户的高层 API；WAV 解析对现代 WAV 不健壮；除 MP3 与 Ogg/Opus 外基本没有标签能力（WAV、M4A 的 `WriteMetadata` 是占位）；FLAC 没有容器写入器。
- **危害**：用户"打开一个 wav 改成 mp3"这种最常见需求，目前只能在 AudioStudio 客户端里拼装，库本身没有一条清晰的调用路径；带标签/浮点/EXTENSIBLE 头的 WAV 会直接解析失败。
- **建议路线**：
  1. **新增高层门面** `AudioFile`：`Open(path)` → `Decode()` → `Process()` → `Encode(format)` → `Save(path)`，内部自动做容器+编解码+格式转换，底层现有 reader/writer 保持不变。
  2. **WAV 解析重写为真正的 RIFF 遍历**（逐块读、跳过未知块、识别 `fmt` 大小 16/18/40、支持 `0xFFFE` EXTENSIBLE、IEEE float、RF64），并补 `LIST/INFO` 标签读写。
  3. **补齐容器写入器**：`FlacFileWriter`（复用 `FlacCodec`），Ogg 标签（Vorbis comment）读写。
  4. **补常用容器**：AIFF/CAF（macOS 交换）、AMR-NB/WB（移动端录音）。
- **代价**：门面 API 一旦发布就是长期契约，需要先定好命名与返回值；WAV 重写会牵动现有测试。

#### G3 Opus 不是"已支持"，是"能借助 ffmpeg"

- **现象**：托管侧只完成包结构解析与范围编解码器；真正编解码走 `ffmpeg` 子进程。
- **危害**：没有 ffmpeg 的机器（几乎全部 Android/iOS 应用、多数容器镜像、干净的 Windows）等于不支持 Opus；子进程方案还有启动开销、并发受限、无法流式低延迟。
- **建议路线**：按已有里程碑 M2~M5 推 CELT 解码 → CELT 编码 → SILK 解码 → SILK 编码。如果短期必须可用，**降级顺序建议为**：系统能力（Android `MediaCodec` / iOS `AudioConverter` 原生支持 Opus）→ 子进程 ffmpeg → 明确报"不支持"。绝不能默认依赖 ffmpeg。
- **代价**：CELT+SILK 是真正的工程量（数千行 + 严格比特一致性测试），是整个项目最难的一块。

### P1：影响成品质感

#### G4 MP3 编码音质不达标

- **现象（已大幅收敛）**：早期端到端 15.4 dB、白噪 3 dB，根因是 MDCT 重叠历史与熵编码缺陷（IMP-001 已闭环）。补齐 481 点滤波器组、M/S 联合立体声、VBR/ABR + Xing 信息帧、简化心理声学模型（掩蔽扩散 + 绝对听阈）后，质量门禁口径（1 kHz 正弦+白噪）达 13.8 dB，纯正弦 45 dB。
- **剩余缺口**：只做长块，瞬态（打击乐/爆破音）会糊——即 CODEC-6d 短块与窗口切换，属专项排期。
- **验收口径**：CODEC-14 门禁（SNR + 相关度 + 实时因子）守回归，短块改造后需再加瞬态信号用例。

#### G5 采样格式模型太薄

- **现状（2026-10-26）**：显式 `SampleFormat`、浮点标记、`AudioFormat.IsPlanar`、有效位、声道掩码与 `AudioFrame` 均已落地，DSP-13 闭环。
- **现象**：`AudioFormat.BitsPerSample=32` 分不清 Int32 与 Float32；无平面格式；24 bit 与浮点之间缺少明确的转换契约。
- **危害**：设备 I/O 与 DSP 之间靠"约定"传数据，一旦接 WASAPI（天生浮点）或 Android（天生 Int16/浮点），必然出现"数据被当错类型解释"的隐性 bug；这也是后续接各平台后端的前置条件。
- **建议路线**：`AudioFormat` 增加显式采样类型（`Int16/Int24/Int32/Float32`）与交错/平面标记；DSP 与设备层统一按浮点交错内部处理，边界处转换。
- **代价**：改的是全库最核心的类型，需要一次性的兼容性设计（新增属性 + 保留旧属性语义）。

#### G6 TTS 缺移动端系统引擎、缺压缩输出

- **现状（2026-10-26）**：MP3/FLAC 压缩输出已接入并经质量门禁验收；仍没有 Android `TextToSpeech` 与 iOS `AVSpeechSynthesizer`。
- **现象**：Windows SAPI / macOS say / Linux espeak-ng + 云端 + 子进程 + 可选 sherpa；没有 Android `TextToSpeech`、没有 iOS `AVSpeechSynthesizer`；输出只到 WAV/PCM（TTS-13 分阶段，输出管线见 TTS-23）。
- **危害**：移动端是 TTS 最高频的场景（离线、免费、系统音色好），目前完全空白；网络流式场景需要 Opus/MP3，只能自己接。
- **建议路线**：移动端两个引擎随第 8 章的平台 TFM 一起做（工作量很小，各约 100~200 行封装）；压缩输出按"网络用 Opus、分发用 MP3/FLAC"分批接入，等 G3/G4 达标后再做。
- **代价**：几乎无风险，收益直接。

#### G7 DSP 高档项缺失

- **现状（2026-10-26）**：线性 + 加窗 Sinc 两档重采样与 EBU R128 响度测量/归一化已落地；混响仍未做。
- **现象**：重采样只有线性；无响度归一化（EBU R128）；无混响。
- **危害**：线性重采样在 44.1k↔48k 这种非整数比下会有明显高频损失与混叠，做音乐类场景会露馅。
- **建议路线**：先补多相/加窗 Sinc 重采样（这是最常用的高质量算法），再考虑 R128 响度；混响按需求再说。
- **代价**：算法明确、风险低，属于"补作业"。

### P2：按需推进

#### G8 ASR 只做适配层，不自研模型

- **现状（2026-10-26）**：`ISpeechRecognizer`、流式端点/部分结果、Windows 系统识别与 sherpa-onnx 离线包适配已落地；Android/iOS 系统识别待平台 TFM。
- **现象与定位调整**：原需求文档把 ASR 列为"不做"；本轮已改为**低优先级、只做接口适配层**：定义 `ISpeechRecognizer`（流式 PCM 进、文本/部分结果出），由可选包对接系统能力（Windows `System.Speech.Recognition` / Android `SpeechRecognizer` / iOS `SFSpeechRecognizer`）或 sherpa-onnx。核心库不引模型、不引推理运行时。
- **理由**：自研离线 ASR 等于造一个新项目；而"接口 + 系统能力适配"能在保持代码纯净的前提下覆盖大部分场景。

#### G9 编解码与容器覆盖缺口

- **现状（2026-10-26）**：AIFF 双向读写与 CAF 读取已补齐；AMR-NB/WB、G.729、ALAC、AC-3 仍未做。
- AMR-NB/WB（移动端/固话录音）、G.729（老式 VoIP）、ALAC（Apple 无损）、AC-3（影视）：都属"有需求再做"，不建议主动铺开。
- AIFF/CAF 建议随 G2 一起补（成本低、macOS 场景刚需）。

### 5.2 设备 I/O：能力协商 + 双流模型

目标形态：

```text
AudioDeviceManager
  ├─ AudioDriverFactory（运行时探测）
  │    ├─ WasapiDriver（共享模式播放/采集/loopback）
  │    ├─ WaveOutNativeDriver（保留兼容）
  │    ├─ AlsaDriver / CoreAudioDriver / AAudioDriver / AVAudioDriver
  │    └─ AsioDriver（后置）
  └─ IAudioPlayer / IAudioRecorder
       ├─ 推模式：Write(Byte[]) / DataAvailable（兼容现有）
       └─ 拉模式：IAudioRenderSource / IAudioCaptureSink（预分配、低延迟）
```

**设计决策**：

1. **运行时选择，禁止编译期猜测**：使用 `OperatingSystem.IsWindows()` / `IsLinux()` / `IsMacOS()` / `IsAndroid()` / `IsIOS()`；每个后端通过可选能力接口实现 `IsSupported`，不支持时明确抛 `PlatformNotSupportedException` 或返回不可用，不再用假设备兜底。
2. **能力描述而非布尔值**：`AudioDeviceInfo` 增加 `Kind`、`IsDefault`、`SupportedFormats`、`MinBufferFrames`、`SupportsLoopback`、`SupportsExclusive`；`AudioFormat` 使用 5.4 的显式采样格式。调用方先查能力再开流。
3. **格式协商在边界完成**：设备 mix format（WASAPI 天生浮点、AAudio 常见 Int16/浮点）→ 库内 Float32 交错；若设备不支持目标格式，由边界重采样/转换，不把“格式不匹配”留给调用方猜。
4. **推拉双模型**：现有 `Write`/`DataAvailable` 保留；新增回调式 `IAudioRenderSource.Read(Span<Single>)` 与 `IAudioCaptureSink.Write(ReadOnlySpan<Single>)`，由后端音频线程直接驱动。回调内零分配、零锁、零日志；需要跨线程时用预分配环形缓冲。
5. **生命周期状态机**：`Created → Initialized → Running → Paused → Stopped → Disposed`，非法转换抛 `InvalidOperationException`；`Stop` 必须可重入、可重复调用。
6. **热插拔与默认设备变化**：`AudioDeviceManager.DevicesChanged` 事件；正在使用的设备被拔除时，播放器进入 `Stopped` 并给出原因，录制器产出已采集数据后停止；是否自动切默认设备由调用方策略决定。
7. **WASAPI 是 Windows 第一优先**：`IMMDeviceEnumerator` 枚举、`IAudioClient` 共享模式、事件驱动、`AUDCLNT_STREAMFLAGS_LOOPBACK` 回采；ASIO 只服务专业低延迟场景，排在 WASAPI 之后。
8. **跨平台顺序**：Windows WASAPI → Linux ALSA → Android AAudio → macOS AudioQueue → iOS AVAudioEngine；每上一个后端都必须进真实设备矩阵。

**后端优先级与验收**：

| 后端 | 关键能力 | 优先级 | 验收 |
|---|---|---|---|
| WinMM | 现有播放/采集兼容 | 保持 | 现有测试不回归 |
| WASAPI | 枚举、共享播放/采集、loopback、设备变化 | P0 | 真实声卡播放/录制；loopback 抓系统声音；拔插恢复 |
| ALSA | 播放/采集、xrun 恢复 | P0 | 无声卡容器用 `null`/`default` 设备；xrun 计数 |
| AAudio | 低延迟回调、设备变化 | P1 | Android 真机往返延迟与欠载统计 |
| AudioQueue/CoreAudio | 播放/采集、默认设备变化 | P1 | macOS 真机 |
| AVAudioEngine | 播放/采集、中断/路由变化 | P1 | iOS 真机，含来电中断 |
| ASIO | 专业低延迟 | P2 | 有 ASIO 驱动的 Windows 真机 |

### 5.3 文件门面：Probe → Read → Process → Write

已落地的调用链（以源码签名为准）：

```csharp
var file = AudioFile.Open(path);                  // 自动探测容器/编码
var info = file.Info;                             // 容器/编码/格式/时长/标签/CanSeek
var pcm = file.ReadPcm();                         // 解码为统一 PCM 视图
pcm.ApplyGain(0.8f);                              // AudioPcm 无损内容操作
AudioFile.WritePcm(newPath, pcm, new AudioWriteOptions
{
    Mp3BitrateKbps = 128,
    PreserveMetadata = true,                      // 默认保留源标签与未知块
});                                               // 临时文件 + 原子替换
```

**设计决策**（目标形态；实际落地 API 与差异见上）：

1. **探测优先级**：魔术字节 > 容器解析 > 扩展名；`Probe` 返回 `AudioStreamInfo` 与置信度，未知格式明确报错，不再回退 `RawPcmReader` 猜测（`AudioProbe` 与 `AudioContainerFactory` 均已如此，FIX-009 已修）。
2. **编码帧与 PCM 双视图**：读取器保留 `ReadFrame()`（编码帧），门面提供 `ReadPcm()`（PCM）与 `StreamPcm()`（分块流式 PCM）；需要 remux 时直接走编码帧，不经过解码。`StreamPcm` 对逐帧可解的容器（WAV/RF64、AIFF、CAF、MP4/AAC）真流式，MP3/FLAC/Ogg/ADTS 仍整段解码后分块。
3. **随机定位**：优先使用容器索引（MP3 Xing/Info/VBRI、Ogg granule、MP4 stco、FLAC SEEKTABLE）；无索引时扫描建索引并缓存；`CanSeek=false` 的流禁止 `Seek`，提前报错。
4. **WAV 重写为 RIFF 遍历**：逐块读 `id/size`，`fmt` 支持 16/18/40 字节，识别 `0xFFFE` EXTENSIBLE、IEEE float、24 bit、RF64；跳过 `fact`/`bext`/未知块；`LIST/INFO` 映射到 `AudioMetadata`。
5. **标签与内容解耦**：`AudioMetadata` 统一模型；仅改标签时写临时文件后原子替换，音频帧原样保留、不重新编码；容器不支持标签时明确返回“不支持”，不静默丢弃。
6. **remux 优先**：MP3/AAC/Opus 在采样率、声道、编码参数一致时按帧复制；参数不一致才解码→重编码，并在 `AudioFileResult` 中报告 `Remuxed/Reencoded`（当前已支持 MP3/ADTS/WAV/Ogg Opus）。
7. **原子保存**：写临时文件（同目录、同扩展名），成功后 `File.Replace`/`File.Move`；失败删除临时文件，原文件保持不变。
8. **容器补全顺序**：FLAC 写入器（复用 `FlacCodec`）→ AIFF/CAF → AMR-NB/WB；每种格式先补“读→写→外部工具回读”闭环，再谈编辑。

### 5.4 采样格式：显式类型 + 平面标记 + 边界转换

目标模型：

```csharp
public enum SampleFormat
{
    UInt8, Int16, Int24, Int32, Float32, Float64
}

public class AudioFormat
{
    public Int32 SampleRate { get; set; }
    public Int32 Channels { get; set; }
    public SampleFormat SampleFormat { get; set; } = SampleFormat.Int16;
    public Boolean IsPlanar { get; set; }
    public Int32 ValidBitsPerSample { get; set; }
    public Int32 ChannelMask { get; set; }
    public Int32 SamplesPerFrame { get; set; }

    // 兼容旧属性：读写时映射到 SampleFormat
    public Int32 BitsPerSample { get; set; }
}
```

**兼容规则**：

- 旧 `BitsPerSample=32` 且 `IsFloat=false` 映射为 `Int32`；浮点需显式设 `IsFloat=true`，`SampleFormat` 由 `PcmConverter.FromBits` 只读推导。
- 旧构造函数/对象初始化器继续可用；`SampleFormat` 的平面标记/有效位等扩展仍按 5.4 目标模型推进。
- `AudioFrame` 统一携带 `AudioFormat`、`TimeSpan Timestamp`、`ReadOnlyMemory<Byte>` 缓冲与所有权标记；需要 `Span<Single>` 视图时由使用方在生命周期内获取；跨线程传递时明确是否池化归还。

**转换契约**：

| 边界 | 输入 | 内部 | 输出 |
|---|---|---|---|
| 设备 | 设备 mix format | Float32 交错 | 设备格式 |
| 容器/编解码 | 文件编码格式 | Float32 交错 | 编码器要求格式 |
| DSP/VOP | Float32 交错 | Float32 交错 | Float32 交错 |
| 平面格式 | planar | 先转交错 | 需要时再转 planar |

**落地状态（2026-10-26）**：`SampleFormat`（由位深 + `IsFloat` 只读推导）、`AudioFormat.IsPlanar`/`ValidBitsPerSample`/`ChannelMask`、`PcmConverter` 的字节↔浮点与交错/平面互转、`AudioPcm` 统一载体，以及 `AudioFrame`（格式 + 时间戳 + 缓冲所有权）均已落地，DSP-13 闭环。

**验收**：8/16/24/32/float/double、planar/interleaved 全组合往返；24 bit 有效位；削波与 NaN/Inf 处理；旧 API 行为不变。

### 5.5 DSP：保留拉取链，补质量与可观测性

现有 `IAudioProcessor` 已经是拉取模型（`Read(Single[], offset, count)`），与 NAudio `ISampleProvider` 同构，不需要推翻。需要补的是：

1. **延迟与尾部声明**：新增可选接口 `IAudioProcessorInfo { Int32 LatencyFrames; Int32 TailFrames; }`，`AudioPipeline` 汇总总延迟；重采样、AEC、FIR 滤波器必须实现。
2. **状态与冲刷**：可选 `IAudioFlushable { void Flush(); }`，文件结束/切换流时把内部缓冲吐完，避免尾部样本丢失。
3. **参数平滑**：增益、EQ、压缩器参数按块线性/指数过渡，禁止逐样本跳变造成 zipper noise；`VolumeControl` 先落地。
4. **高质量重采样**：多相 FIR + Kaiser 窗，支持有理数 L/M、任意比率、质量档（Fast/Balanced/High）；High 档通带纹波 <0.1 dB、阻带 >80 dB，报告群延迟；用 SoX/NAudio 输出做参考对照。
5. **响度**：BS.1770-4 K 加权、400 ms 门控块，输出 Integrated/Momentary/ShortTerm/TruePeak；归一化采用“测量→增益→真峰值限幅”，默认不自动插入管线。
6. **声明式组合**：提供 `AudioPipelineBuilder` 的命名阶段（`AddResample`/`AddEq`/`AddCompressor`），不解析 SoX CLI；配置只描述顺序与参数，实际仍是 `IAudioProcessor` 链。

**落地状态（2026-10-26）**：当前 `Resampler` 为 Blackman 窗加窗 Sinc（核半长 16，即 32 抽头），未实现多相 FIR/Kaiser 与 Fast/Balanced/High 质量档；DSP-14 按需求口径（加窗 Sinc）验收。

**验收**：重采样扫频/白噪/正弦指标；响度与 EBU R128 参考实现误差 ≤0.5 LU；稳态 `Read` 零分配；管线顺序与旁路可回归。

### 5.6 语音前处理：帧对齐 + 模块化 + 客观指标

借鉴 WebRTC APM 的模块化与 SpeexDSP 的轻量实现，但保持纯托管：

```text
FarEnd ──→ [延迟对齐] ──┐
                        ├─→ [HPF] → [AEC] → [NS] → [AGC] → [VAD] → NearEnd
NearEnd ──→ [10ms 分帧] ─┘
```

**设计决策**：

1. **统一 10 ms 帧**：8/16/32/48 kHz 下按 10 ms 取帧；变帧长在入口转换，模块内部不各自缓存。
2. **AEC 必须吃远端参考**：`Process(NearEnd, FarEnd)` 双输入；延迟估计、双讲检测、舒适噪声、失锁恢复作为独立状态；输出 ERLE、双讲衰减、收敛标志。
3. **模块可插拔**：每个模块独立开关与参数，`VoicePreprocessor` 只负责编排与帧对齐；模块之间不共享隐式状态。
4. **VAD 与端点**：GMM VAD 输出语音/非语音与 hangover；上层可做端点检测；与 WebRTC VAD 在固定测试集上对比误检/漏检。
5. **质量门禁**：合成回声 ERLE ≥ 20 dB（单讲、16 kHz、固定样本），双讲期间近端语音衰减 ≤ 3 dB，NS 不引入明显音乐噪声，AGC 无明显泵动；所有指标进回归报告，不只看“能跑”。

### 5.7 Opus：最小 API + 分层实现 + 明确降级链

**API 形状**（内部实现，不改变现有 `OpusCodec` 门面）：

```csharp
public interface IOpusEncoder : IDisposable
{
    OpusEncoderConfig Config { get; }
    Int32 Encode(ReadOnlySpan<Single> pcm, Span<Byte> packet);
}

public interface IOpusDecoder : IDisposable
{
    OpusDecoderConfig Config { get; }
    Int32 Decode(ReadOnlySpan<Byte> packet, Span<Single> pcm); // packet 为空 = PLC
}
```

**分层**：

- `OpusCodec`：公共门面、参数校验、帧长/pre-skip/lookahead、降级选择。
- `OpusManagedCodec`：能力开关；CELT/SILK 按 M2~M5 逐步启用。
- `OpusRangeEncoder/Decoder`：已完成的熵编码基础。
- `OpusPlatformCodec`（新增）：Android `MediaCodec` / iOS `AudioConverter` 适配。
- `OpusProcessCodec`：ffmpeg 子进程，仅兜底。

**降级顺序**（必须写进能力查询与日志）：

| 顺序 | 实现 | 条件 | 失败行为 |
|---|---|---|---|
| 1 | 托管 CELT/SILK | M2~M5 能力就绪 | 继续下一层 |
| 2 | 平台原生 Opus | Android/iOS 且系统支持 | 继续下一层 |
| 3 | ffmpeg 子进程 | 显式可用且允许子进程 | 继续下一层 |
| 4 | 不支持 | 以上都不可用 | `NotSupportedException`，消息说明缺什么 |

**质量与性能**：

- RFC 6716 测试向量、ffmpeg/libopus 双向互操作、CELT/SILK 分层样本。
- 范围编码器逐位一致；浮点解码按容差比较。
- 实时因子、稳态分配、AOT 冒烟；FEC/PLC/DTX 单独测试，不与普通编解码混在一起。

### 5.8 TTS/ASR：能力描述 + 流式管线

**TTS**：

- `ITtsEngine` 增量提供 `TtsEngineCapabilities`（音色、语言、输出格式、是否支持流式/SSML/词边界）；调用方先查能力再选引擎。
- 输出管线：`TtsChunk` → 可选重采样/格式转换 → `IAudioSink`（WAV/流式 WAV/Opus/MP3/FLAC）→ 文件或网络；支持背压、取消、首包延迟统计。
- 移动端 `TextToSpeech`/`AVSpeechSynthesizer` 随平台 TFM 提供；核心库不引模型。
- 压缩输出：MP3/FLAC 已接入并经 CODEC-14 门禁验收；Opus/AAC 待托管编码器或场景明确后接入，能力查询如实返回。

**ASR**：

- `ISpeechRecognizer` 输出部分结果/最终结果、时间戳、置信度、端点事件；输入为 PCM 帧，可直接接 VOP 前处理。
- 系统识别与 sherpa-onnx 可选包实现同一接口；核心库零推理依赖。
- 端点检测与 VAD 解耦：VAD 负责“有没有人声”，端点负责“一句话是否结束”。

## 6. 依赖策略：三级降级

你的原则是"纯托管优先 → 必要时用 OS 能力 → 最后才 P/Invoke"。落地成四条规则：

1. **能用纯托管就纯托管**，且算法必须有测试或外部工具互操作验证（互操作验证比自测更能发现"自己编码自己能解"的假正确）。
2. **OS 能力优于 P/Invoke**：同样调系统，优先选托管绑定稳定的路径——`System.Speech` 反射、Android/iOS 的托管绑定、`say`/`espeak-ng` 子进程，都算 OS 能力层。
3. **P/Invoke 必须隔离**：要么条件编译进平台 TFM，要么放进独立可选包；绝不能让主包在无原生库时报 `DllNotFoundException`。
4. **子进程（ffmpeg/piper/espeak）只能做降级，不能做主路径**：它引入环境依赖，且无法满足流式低延迟。

| 能力 | 理想（纯托管） | 兜底（OS 能力） | 最后手段（P/Invoke） | 当前选择 |
|---|---|---|---|---|
| 常用编解码 | ✅ 已达成（G.711/G.722/G.726/ADPCM/MP3/AAC/FLAC/Vorbis/Speex） | 平台 MediaCodec/AudioConverter | 原生库 | **纯托管为主**，Opus 例外 |
| Opus | ❌ 未完成（M2~M5） | Android MediaCodec / iOS AudioConverter | libopus | **托管优先；平台原生为第一降级；ffmpeg 仅兜底**（见 5.7） |
| 播放/录音 | ❌ 不可能（必须碰系统） | winmm / WASAPI / ALSA / CoreAudio / AAudio / AVAudio | — | **Windows：winmm + WASAPI 已实现；Linux：ALSA 已实现（🟡 待真机验证）**；macOS 与移动端空白 |
| TTS | ❌ 不现实（模型太大） | SAPI / say / espeak / Android TTS / AVSpeech | 原生推理库 | **系统能力 + 云端**（正确选择） |
| ASR | ❌ | 系统识别 / sherpa-onnx 可选包 | 原生推理库 | **Windows 系统识别 + sherpa 离线包已适配**；移动端待平台 TFM |

**现存例外与处置**：

| 项 | 状态 | 处置建议 |
|---|---|---|
| `FaacEncoder`（8 处 `DllImport` 调 libfaac） | 已 `[Obsolete]`，主链路不再使用；仓库仍提交 `NewLife.Audio/AAC/libfaac.dll`（84 KB，无 csproj 引用） | 下个大版本删除类型并移除 DLL；`AacCodec` 纯托管编码已可替代 |
| AAC 解码的 SharpJaad 内核（MIT 源码移植，不是 NuGet 包） | 合规，但仓库无第三方声明 | 补 `THIRD-PARTY-NOTICES` 或在 README 致谢，避免许可争议 |
| `NewLife.Audio.Sherpa`（sherpa-onnx 原生推理） | 独立可选包，核心库零依赖 | 保持隔离，文档明确"非核心能力" |
| 测试工程的 NVorbis / OggVorbisEncoder | 仅测试与互操作对照 | 不进发布包，无需处理 |

## 8. 移动端目标框架怎么落地

### 8.1 结论

**可以把 `net8.0-android` / `net8.0-ios` 直接加进主库，但必须"条件多目标"，并且只在 CI 里出这两个 TFM。**

如果无条件写进 `TargetFrameworks`，那么任何没装 workload 的开发者在仓库根目录执行 `dotnet build` 都会直接失败（NETSDK1147：缺少 android / ios workload），VS/Rider 加载也会报错。这不是"可以不编译"能绕过的——默认构建就是全 TFM。

### 8.2 推荐做法（方案 A：主库条件多目标）

```xml
<!-- 默认只编可移植 TFM，任何机器都能 build -->
<TargetFrameworks>net8.0;netstandard2.1;netstandard2.0;net461</TargetFrameworks>

<!-- 只有显式开启时才追加移动端 -->
<TargetFrameworks Condition="'$(EnableMobile)' == 'true'">$(TargetFrameworks);net8.0-android;net8.0-ios</TargetFrameworks>
```

平台代码用条件编译隔离：

```csharp
#if ANDROID
    // Android.Media.AudioTrack / AudioRecord / AAudio
#elif IOS
    // AVFoundation.AVAudioEngine / AVAudioSession
#endif
```

CI 分工：

| 任务 | 运行环境 | 命令 |
|---|---|---|
| 日常构建 / 单测 | Windows、Linux、macOS（已有矩阵） | `dotnet build`（默认 4 TFM，零 workload） |
| Android 编译与冒烟 | 任意 OS（装 android workload） | `dotnet build -p:EnableMobile=true -f net8.0-android` |
| iOS 编译与冒烟 | **必须 macOS runner** | `dotnet build -p:EnableMobile=true -f net8.0-ios` |
| 打包 NuGet | **必须 macOS**（能同时编 android + ios） | `dotnet pack -p:EnableMobile=true` |

**必配守卫**：在 `tools/check-package-consumer.ps1` 增加"包内 `lib/` 必须同时包含 `net8.0-android` 与 `net8.0-ios`"断言，防止有人在 Windows 上误出包，发布一个缺移动端资产的版本（这类事故极难事后发现）。

### 8.3 备选做法（方案 B：独立平台包）

主库永远保持 4 个可移植 TFM；新增 `NewLife.Audio.Mobile` 项目，TFM 为 `net8.0-android;net8.0-ios`，通过反射注册驱动：

```csharp
// 核心库不引用移动包，靠约定类型名发现
var type = Type.GetType("NewLife.Audio.Mobile.AndroidAudioDriver, NewLife.Audio.Mobile");
```

### 8.4 怎么选

| 维度 | A：主库条件多目标 | B：独立平台包 |
|---|---|---|
| 用户要装几个包 | 1 个 | 2 个 |
| 桌面开发者编译体验 | 默认 4 TFM，完全无感 | 完全无感（更彻底） |
| 平台代码访问权限 | `#if ANDROID` 直接写，最自然 | 必须走反射/接口，稍绕 |
| 发版链路 | 必须引入 macOS 打包机 | 各平台可独立打包 |
| 版本一致性风险 | 无（同一包） | 两个包必须同步版本 |
| 适合场景 | 移动端是主线能力 | 移动端是可选增强 |

**推荐 A**：本项目的目标明确包含移动端播放录音，平台代码写在主库里最自然；代价只是发版要用 macOS，这一点本来就绕不过（iOS 只能在 macOS 编译）。
