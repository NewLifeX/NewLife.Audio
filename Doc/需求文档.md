# NewLife.Audio 需求文档

本文档描述 NewLife.Audio 的愿景、核心目标和模块划分。完成状态在[功能模块清单](功能模块清单.md)中追踪，详细设计在各模块架构文档中展开。

## 1. 背景与愿景

### 1.1 系统定位

NewLife.Audio 是一个**跨平台 .NET 全功能音频处理库**，面向 .NET 开发者提供编解码、设备 I/O、DSP 效果、语音处理、语音合成编排、容器格式读写、流媒体传输等一站式音频能力。纯托管 C# 优先，NuGet 一键安装即用，无原生依赖门槛。

### 1.2 愿景

- **跨平台统一体验**：一份代码跑通 Windows / Linux / macOS / Android / iOS，开发者无需关心底层音频后端差异
- **纯托管优先**：常用算法全部 C# 实现，降低部署成本；仅对性能/质量敏感场景（如 AEC）可选包装原生库
- **IoT 深度兼容**：延续海思芯片头处理基因，扩展大华/宇视等厂商适配，服务物联网音视频场景
- **信号链可组合**：借鉴业界成熟的信号链模式，让编解码、DSP、语音处理模块像搭积木一样自由组合。

### 1.3 竞品借鉴与优先级

> 依据[竞品分析报告](竞品分析报告.md)第 3 节与[架构设计](架构设计.md)第 4 章差距清单整理。只吸收能直接补齐自身短板的成熟做法，不按竞品功能数量逐项对标。

| 优先级 | 我们的差距 | 借鉴对象与关键做法 | 对应需求 |
|---|---|---|---|
| P0 | G1 设备 I/O 只有 WinMM 一条真实路径 | PortAudio 的统一设备能力查询与回调/阻塞双模型；NAudio 的播放后端与数据源解耦；WASAPI 共享模式与 loopback | DEVIO-13~15 |
| P0 | G2 文件“读→改→写”闭环不成型 | libsndfile 的虚拟 I/O 与格式探测；FFmpeg 的 probe/seek/remux；NAudio `WaveStream` 的定位与长度模型 | CONT-8~11、FILE-6~7 |
| P0 | G3 Opus 实际依赖 ffmpeg | Opus 的最小 API、帧级处理与编解码器独立生命周期；平台原生 Opus 作为 OS 能力层 | CODEC-13~14 |
| P0 | G5 采样格式模型太薄 | FFmpeg `AVSampleFormat` 的显式采样类型与 planar/interleaved；PortAudio 的格式能力查询 | DSP-13 |
| P1 | G4 MP3 编码音质不达标 | LAME 的心理声学模型、scalefactor band、M/S 立体声、比特池与短块 | CODEC-14 |
| P1 | G6 TTS 缺移动端引擎与压缩输出 | 平台系统 TTS；sherpa-onnx 的可选离线模型隔离 | TTS-23 |
| P1 | G7 DSP 缺高质量重采样与响度 | SoX 的多相/加窗 Sinc 与 EBU R128；NAudio 的 WdlResampling；WebRTC 的模块化前处理 | DSP-14~15、VOP-7 |
| P2 | G8 ASR 只做适配层 | sherpa-onnx 的流式识别、端点检测与部分结果 | ASR-4 |
| P2 | G9 编解码/容器覆盖缺口 | libsndfile/FFmpeg 的容器覆盖；AMR、AIFF/CAF 按场景补齐 | FILE-4、CONT-11 |

**取舍原则**：

1. **先修承诺，再扩功能**：G1/G2/G3/G5 属于“对外承诺与真实能力不一致”，优先于新增编解码格式。
2. **只借架构，不借依赖**：借鉴接口形状、分层与验收方法，不引入第三方音频运行时；Opus 平台原生能力仅作降级层。
3. **一项能力一个抽象**：设备、文件、采样格式、信号链各只增加一层核心抽象，避免竞品式的多套并行 API。
4. **验收先于宣称**：每项能力必须有外部工具、真实硬件或参考向量的验收口径，未达标不得在功能清单标记 ✅。

## 2. CODEC 编解码引擎

音频编解码是库的核心能力，提供 PCM ↔ 各种编码格式的双向转换。

- **CODEC-1 PCM ↔ G.711 μ-law 编解码**：完整的双向 G.711 μ-law 编解码，包含查表法线性↔μ-law 互转。
- **CODEC-2 PCM ↔ G.711 A-law 编解码**：已有完整实现，维持现有 `G711ACodec`。
- **CODEC-3 PCM ↔ IMA ADPCM 编解码**：已有完整实现，维持现有 `ADPCMCodec`。
- **CODEC-4 AAC 编解码（已落地）**：拆分为以下子项，全部纯托管实现，不引入原生依赖。详见 [AAC 编解码设计](AAC-编解码设计.md)。
  - **CODEC-4a AAC-LC 解码**：ADTS / raw+ASC / MP4-M4A，ICS 解析、完整 Huffman 码表、长短块与窗切换、TNS/PNS/M/S/强度立体声、FFT-IMDCT、每流状态。
  - **CODEC-4b HE-AAC v1/v2 解码**：SBR + PS，服务低码率流场景。
  - **CODEC-4c AAC-LC 编码**：纯托管 MDCT + 量化 + 码率控制 + Huffman + 比特池，输出 ADTS/raw。
  - **CODEC-4d HE-AAC 编码**：SBR + PS 编码，风险最高，最后实施，允许降级。
  - **CODEC-4e AAC 容器集成**：ADTS、raw+ASC、MP4/M4A/3GP 的 `esds` 解析与封装，LOAS/LATM 与 RTP AAC-hbr。
  - **当前状态**：AAC-LC/HE-AAC v1/v2 解码、AAC-LC 编码、ADTS/raw+ASC/MP4-M4A/3GP/LOAS-LATM 容器与 RTP AAC-hbr 已落地并通过外部向量交叉验证；HE-AAC 编码暂缓。
- **CODEC-5 PCM ↔ Opus 编解码**：自研纯托管路线，不引入第三方编解码包。M1 已完成 Opus 包结构解析、范围编码器/解码器与 Ogg Opus 容器互操作；托管 CELT/SILK 按 M2~M5 推进。降级顺序固定为：托管实现 → 平台原生 Opus（Android `MediaCodec` / iOS `AudioConverter`）→ 系统 ffmpeg 子进程 → 明确报“不支持”；不得把 ffmpeg 当默认路径。详见 [OPUS-自研编解码](OPUS-自研编解码.md) 与 CODEC-13。
- **CODEC-6 PCM ↔ MP3 编解码**：纯托管双向实现——解码覆盖 MPEG-1/2/2.5、长短块、联合立体声与比特池；编码为自研 Layer III（多相分析 + MDCT + 标量量化 + Huffman + 帧组装），支持 8k～48k 九档采样率、单/立体声，M/S 联合立体声、CBR/VBR/ABR 与 Xing 信息帧、简化心理声学模型（掩蔽扩散 + 绝对听阈）均已落地；短块与窗口切换（瞬态处理）仍在排期，打击乐/爆破音会偏糊。
- **CODEC-7 PCM ↔ FLAC 编解码**：纯托管 FLAC 编解码完整实现（Fixed LPC + LPC 子帧 + Rice 残差编码 + Mid/Side 立体声 + MD5）。
- **CODEC-8a/8b PCM ↔ Ogg Vorbis 编解码**：纯托管 Vorbis I 实现——解码覆盖三头包、码本、floor0/1、residue 0/1/2、声道耦合、长短块与 IMDCT 重叠相加；编码器提供长块基线（floor1 + residue2 + canonical Huffman），输出可被 NVorbis 解码。详见 [VORBIS-纯托管编解码](VORBIS-纯托管编解码.md)。
- **CODEC-9 PCM ↔ G.722 / G.726 编解码**：电信语音编解码器，纯 C# 完整实现，服务 VoIP/对讲场景。码流为库内自洽的私有格式（子带拆分用简化 QMF、量化与自适应表为自研参数），不与 ITU-T 设备互通；往返质量由 CODEC-14 门禁守护。
- **CODEC-10 PCM ↔ Speex 编解码**：纯托管窄带编解码，20ms 帧 + 4 bit 自适应差分量化（32kbps），多帧码流按「长度前缀 + 帧数据」封装，服务低码率语音场景；码流为私有格式，不与 libspeex 互通。
- **CODEC-11 编解码工厂插件化**：`CodecRegistry` 注册表 + `ICodecInfo` 元数据，支持运行时注册/发现编解码器、按 `AVTypes` 自动路由，区分无状态单例与有状态工厂模式。
- **CODEC-12 芯片音频头适配**：海思 `HisiliconHeader`、大华 `DahuaHeader`、宇视 `UniviewHeader` 完整实现，统一的 `IAudioChipHeader` 接口，自动去头/还原。
- **CODEC-13 Opus 平台原生降级层**：在托管 CELT/SILK 完成前，为 Android/iOS 提供平台原生 Opus 适配（`MediaCodec` / `AudioConverter`），作为 ffmpeg 子进程之前的降级层；无任何可用实现时抛出清晰异常并在能力查询中标注不可用。
- **CODEC-14 编解码质量与互操作门禁**：每个编码器统一验收——标准解码器互操作、参考向量比对、SNR/相关度阈值、实时因子与稳态分配量；Opus 的 FEC/PLC/DTX 单独验证；MP3 编码参考 LAME 的公开算法思路（心理声学模型、scalefactor band、M/S 立体声、比特池与短块），独立实现、不复制代码，未达阈值不得标记完成。
  - **当前状态**：门禁已落地（`CodecQualityGateTests`，9 个编码器 × 质量/实时因子/健壮性三类用例，阈值取实测值下调约 2.5 dB 后固化）；MP3 与 LAME 的逐项心理声学对齐、外部解码器互通向量仍属长线。

## 3. DEVIO 音频设备 I/O

提供播放、录制、设备管理等音频硬件交互能力，提供完整的设备抽象层。目标平台为 Windows / Linux / macOS / Android / iOS，各平台对接系统原生音频 API（Windows：WinMM/WASAPI/ASIO；Linux：ALSA；macOS：AudioQueue/CoreAudio；Android：AAudio；iOS：AVAudioEngine）。Windows 侧 WinMM 与 WASAPI（共享模式播放/采集、loopback、事件回调、设备丢失恢复、热插拔观察）均已实现；ASIO 与其余平台后端尚未实现，状态与排期见[架构设计](架构设计.md)。

- **DEVIO-1 设备枚举与发现**：枚举系统音频输入/输出设备，获取名称、通道数、支持格式等元数据。
- **DEVIO-2 WaveOut 播放**：Windows WaveOut API 封装（`WaveOutNativeDriver`），提供低延迟音频播放。
- **DEVIO-3 WASAPI 播放与录制**：Windows WASAPI 封装（`WasapiDriver`），共享模式播放、采集与系统声音回环录制（`LoopbackRecorder`）均已实现并实测。
- **DEVIO-4 ASIO 低延迟播放与录制**：专业音频 ASIO 驱动封装（`AsioDriver`），面向录音/监听等需要极低延迟的场景。
- **DEVIO-5 跨平台驱动抽象**：统一 `IAudioPlayer`/`IAudioRecorder`/`IAudioDriver` 接口，目标按运行时平台自动选择最优驱动；`AudioDriverFactory` 已改为运行时判断并上报能力，无后端时明确抛不支持（见 DEVIO-13）。
- **DEVIO-6 音频采集**：麦克风录音，通过 `IAudioRecorder` 接口采集。
- **DEVIO-7 环路录制**：系统音频输出回采（`LoopbackRecorder`），用于屏幕录制、直播推流等场景。
- **DEVIO-8 多设备并发管理**：`AudioDeviceManager` 管理多个驱动注册与选择，并发播放/录制互不干扰。
- **DEVIO-9 Linux 原生后端**：ALSA（`libasound`）播放与采集，覆盖无 PulseAudio 的嵌入式与容器环境。
- **DEVIO-10 macOS 原生后端**：AudioQueue/CoreAudio 播放与采集。
- **DEVIO-11 Android 原生后端**：AAudio（API 26+）与 AudioTrack/AudioRecord 播放与采集，支持低延迟模式；平台目标框架方案见[架构设计](架构设计.md) 第 8 章。
- **DEVIO-12 iOS 原生后端**：AVAudioEngine/AVAudioSession 播放与采集，含中断与路由变化处理。
- **DEVIO-13 运行时后端选择与能力上报**：驱动选择改为运行时平台判断；通过可选接口或扩展属性增量暴露 `IsSupported`、后端名称与设备能力（采样率/声道/采样格式/最小缓冲/是否支持 loopback 与独占模式），不破坏既有驱动实现；无可用后端时明确返回“不支持”，不再返回假设备或 `NullRecorder`。
- **DEVIO-14 WASAPI 完整能力**：使用 `IMMDeviceEnumerator` + `IAudioClient` 实现共享模式播放、采集与系统声音回环录制；支持默认/指定设备、格式协商、事件驱动与设备丢失恢复；ASIO 在 WASAPI 达标后再补。
- **DEVIO-15 热插拔与回调式低延迟流**：设备增删、默认设备变化可观测；播放/录制在保留现有 `Write`/`DataAvailable` 推模式的同时，提供预分配缓冲的回调/拉取模式，回调线程不做分配、不加锁，缓冲大小与目标延迟可配置。

## 4. DSP 音频处理

纯托管 C# 实现的音频数字信号处理管线，借鉴业界成熟的信号链组合模式。

- **DSP-1 重采样**：提供线性与加窗 Sinc 两档质量，支持任意采样率互转、有理数比率、抗混叠与延迟报告（DSP-14）；44.1k↔48k 等非整数比由质量测试守护。
- **DSP-2 声道转换**：单声道↔立体声↔多声道互转，支持自定义声道映射矩阵。
- **DSP-3 位深度与采样格式转换**：8/16/24/32 bit 整数与 32 bit 浮点数之间的自由转换。
- **DSP-4 音量控制与增益**：线性/对数增益调节，支持静音检测。
- **DSP-5 混音引擎**：多路音频流按权重混合为一路，支持 32-bit 浮点精度累加后归一化。
- **DSP-6 FFT 频谱分析**：快速傅里叶变换，输出频谱数据用于可视化或音频特征提取。
- **DSP-7 均衡器**：多段参数均衡器，支持低架/峰值/高架滤波器的组合配置。
- **DSP-8 BiQuad 滤波器**：低通/高通/带通/带阻/峰值/低架/高架等标准滤波器。
- **DSP-9 动态范围压缩与扩展**：压缩器/限幅器/噪声门，用于响度控制和动态优化。
- **DSP-10 淡入淡出与交叉淡变**：音频片段平滑过渡，支持线性/对数/余弦等多种曲线。
- **DSP-11 变速与变调**：改变播放速度或音高，且两者可独立控制。
- **DSP-12 信号链管线**：`AudioPipeline` 将多个 DSP 处理器串联为处理链，提供流畅的组合式 API。
- **DSP-13 采样格式模型与统一帧**：`AudioFormat` 增加显式采样类型（U8/S16/S24/S32/F32/F64）、平面/交错标记、有效位与声道掩码；库内统一按 Float32 交错处理，设备/容器/编解码边界显式转换；提供 `AudioFrame`（格式 + 时间戳 + 缓冲所有权）作为设备、DSP、VOP 的公共数据载体。
  - **当前状态**：显式 `SampleFormat`、浮点标记、`AudioFormat.IsPlanar`、有效位与声道掩码已落地；`PcmConverter` 提供字节↔浮点与交错/平面互转；`AudioFrame`（格式 + 时间戳 + 缓冲所有权）已提供，并与 `AudioPcm` 互转。
- **DSP-14 高质量重采样**：在现有线性插值之外提供多相/加窗 Sinc 重采样，支持有理数比率、抗混叠、质量档位与延迟报告；44.1k↔48k 等非整数比下通带/阻带指标需有参考工具对照。
- **DSP-15 响度归一化**：提供 EBU R128 综合/短时/瞬时响度与真峰值近似测量，以及“测量→增益→限幅”的归一化流程；默认不改变现有处理链行为。

## 5. VOP 语音处理

实时语音通信所需的前端处理能力，填补 .NET 生态空白。已全部实现。

- **VOP-1 语音活动检测（VAD）**：检测音频流中的人声片段，纯 C# 实现业界标准的 GMM 模型 VAD 算法。
- **VOP-2 声学回声消除（AEC）**：消除扬声器到麦克风的回声，保证全双工通话质量。纯托管 NLMS 自适应滤波器 + 双讲检测 + 舒适噪声注入，已实现。
- **VOP-3 自动增益控制（AGC）**：自动调节麦克风或输入音频的增益，保持恒定输出电平。
- **VOP-4 噪声抑制（NS）**：抑制稳态背景噪声（风扇、空调等），提升语音清晰度。基础算法纯 C#，高质量方案远期引入 ML 模型。
- **VOP-5 高通滤波**：去除低频直流偏移和次声频噪声。
- **VOP-6 语音前置处理管线**：将 VAD → AGC → NS → 高通滤波组合为即开即用的语音前端处理链。
- **VOP-7 语音前处理工程化**：以 10 ms 帧为基本单位对齐远端参考与近端采集，处理顺序固定为 HPF → AEC → NS → AGC → VAD；AEC 输出可观测的 ERLE、双讲衰减与收敛状态；补齐延迟补偿、舒适噪声与失锁恢复，质量以合成回声/双讲样本的客观指标验收。

## 6. CONT 容器格式

音频容器（文件格式）的读写支持，作为编解码数据的持久化入口。

- **CONT-1 WAV 文件读写**：WAV/PCM 文件读取与写入，支持 PCM/ADPCM/A-law/μ-law 等编码标记；完整 RIFF 遍历、EXTENSIBLE/浮点/RF64 与 LIST/INFO 标签见 CONT-9。
- **CONT-2 Ogg 容器封装与解封**：纯 C# Ogg 容器读写，为 Vorbis 和 Opus 提供容器基础；Vorbis 的 identification/comment/setup 独立头页、granule 与 CRC 已打通。
- **CONT-3 MP4/M4A 容器**：读取和写入 AAC/MP3 音频的 MP4 容器。
- **CONT-4 FLAC 原生容器**：FLAC 容器读取（元数据块、STREAMINFO）与写入（CONT-11）均已实现。
- **CONT-5 原始 PCM 头解析**：无头 PCM 数据的格式由调用方显式指定；不做采样率/位深/声道的启发式推断——猜错会产生"能播放但全错"的音频，比要求显式传参更危险（理由见功能清单收口记录）。
- **CONT-6 MP3 文件读写**：ID3v2 标签读写（标题/艺术家/专辑/流派/年份/音轨/注释/封面）+ MPEG 音频帧索引（精确总帧数与时长，CBR/VBR 通用），支持帧透传写入与 PCM 直接压缩落盘。
- **CONT-7 流式输出写入器**：面向不可 seek 的流（HTTP/WebSocket 边合成边写），提供 WAV / Ogg Opus / MP3 三种流式写入器，由 TTS 与实时推流复用。
- **CONT-8 容器探测与流信息**：提供统一 `Probe` 能力，返回容器、编码、采样格式、时长、码率、标签、可 seek 性与探测置信度；扩展名只作提示，以魔术字节和容器解析为准；无法识别时明确报错，不回退成裸 PCM。
  - **当前状态**：`AudioProbe` 与 `AudioContainerFactory.CreateReader` 均按严格语义实现——魔术字节未识别时明确抛 `NotSupportedException`，不再回退默认参数的 `RawPcmReader`（FIX-009 已修）。
- **CONT-9 WAV 完整 RIFF 解析**：按 RIFF 块顺序遍历，支持 fmt 16/18/40、`WAVE_FORMAT_EXTENSIBLE`、IEEE float、24 bit、RF64、`LIST/INFO`，并跳过 `fact`/`bext` 等未知块；写入端同步支持对应头与标签。
- **CONT-10 虚拟流 I/O**：容器读写器统一支持路径、`Stream` 与回调式数据源/目标，显式暴露 `CanSeek`/`Length`；不可 seek 流走流式写入器，网络与管道场景不要求临时文件。
- **CONT-11 FLAC 容器写入器**：补齐 `FlacFileWriter`，复用 `FlacCodec`，支持流式写入、SEEKTABLE 与 Vorbis comment 标签，不再要求整段编码后一次性落盘。

## 7. FILE 音频文件门面与编辑

把"打开 → 处理 → 保存"收敛成一条清晰调用链，使用方不必自己拼装容器读写器与编解码器。覆盖四类诉求：格式互转、标签修改、无损内容操作（裁剪/拼接/增益/重采样）、批量处理。

- **FILE-1 文件门面**：`AudioFile.Open(path)` 自动识别容器与编码（魔术字节为主、扩展名提示），`ReadPcm()` 得到统一 PCM 视图，`StreamPcm(chunkBytes)` 逐块流式解码（WAV/AIFF/CAF/M4A 逐帧，MP3/FLAC/Ogg 退化为整段解码后分块），`SaveAs(path)` / `WritePcm(path, pcm)` 按目标格式选择编码器与容器；目标为全程流式、不整段载入。
  - **当前状态**：门面与标签保留、原子保存已落地；`ReadPcm()` 仍整段解码到内存（适合随机访问），长文件改走 `StreamPcm()` 按块拉取，WAV/AIFF/CAF/M4A 为真流式。
- **FILE-2 标签读写**：统一的 `AudioMetadata` 模型，覆盖 MP3（ID3v2.4/ID3v1）、FLAC 与 Ogg（Vorbis comment）、M4A（iTunes 原子）、WAV（LIST/INFO）；支持"只改标签、不重新编码"。
- **FILE-3 无损内容操作**：按时间或帧裁剪、同格式拼接（异格式先统一 PCM）、增益、采样率与声道转换；MP3/AAC 在参数一致时走帧级复制，不重新编码。
- **FILE-4 容器补全**：AIFF 双向读写、CAF 读取（macOS 生态）、WAV 支持 RF64/`WAVE_FORMAT_EXTENSIBLE` 与浮点（CONT-9）、FLAC 容器写入器（CONT-11）均已落地；AMR-NB/WB 不做（需先解决编解码与专利授权，见收口记录）。
- **FILE-5 批量与进度**：多文件顺序/并发转换，提供进度回调与取消。
- **FILE-6 元数据保留与原子保存**：读→处理后保存默认保留源标签与未知块；仅改标签时写临时文件后原子替换，不重新编码；保存采用临时文件 + 原子替换，失败不破坏原文件。
- **FILE-7 帧级复制与重封装**：MP3/AAC/Opus 在编码参数一致时支持帧级复制（裁剪/拼接/容器转换不重编码）；参数不一致时明确回退到解码→重编码，并在结果中报告实际路径。
  - **当前状态**：MP3→MP3、ADTS→ADTS、WAV→WAV 与 Ogg Opus→Ogg Opus 均已支持帧复制；Ogg Opus 会逐包复制并重写 Opus 头/标签。

> 现状：门面、标签层、无损内容操作与批量转换均已落地——`AudioFile` 打通"打开→解码→处理→保存"，读→改→写默认保留源标签与未知块，仅改标签走原子重写不重编码，MP3/AAC 参数一致时走帧级复制并回报实际链路。

## 8. STRM 流媒体与传输

音频网络传输能力，服务实时对讲、直播推流、IoT 设备上报等场景。已全部实现。

- **STRM-1 RTP 音频包封装与解析**：按 RFC 标准将音频帧封包为 RTP 包，支持 G.711/Opus/AAC 等 Payload Type。
- **STRM-2 RTSP 音频流**：RTSP 协议客户端，拉取或推送音频流。
- **STRM-3 HTTP 音频流**：HTTP 实时音频流（Shoutcast/Icecast 风格），支持分段传输和流式播放。
- **STRM-4 WebSocket 音频推送**：基于 WebSocket 的双向低延迟音频传输，服务 Web 端实时通话。
- **STRM-5 抖动缓冲**：按序重组、去重、丢包率与当前延迟统计，平滑网络抖动。

## 9. TTS 语音合成

把“文本变成声音”做成一条极简流水线：普通用户三行代码出声，高级用户再通过引擎注入与选项深入配置。定位仍是**引擎编排与集成层**：统一抽象 + 系统语音 + 文件/流式输出 + 可选缓存与文本规范化，具体合成由系统语音、子进程工具或在线服务提供。核心库不内置模型权重，也不依赖 ONNX Runtime。

三个主入口全部异步，统一签名 `(text, options = null, cancellationToken = default)`：

```csharp
var tts = new TtsClient();
await tts.SayAsync("设备A2温度过高");              // 直接播报
await tts.SaveAsync("设备A2温度过高", "alert.wav"); // 保存文件
await foreach (var chunk in tts.StreamAsync("...")) { } // 流式输出 PCM
```

- **TTS-1 极简客户端**：`TtsClient` 提供 `SayAsync` / `SaveAsync` / `StreamAsync` / `GetVoices` / `Stop`，默认按平台自动选择系统语音；`TtsClient.Default` 提供全局默认实例。
- **TTS-2 系统语音引擎**：Windows 通过反射调用 SAPI（`System.Speech`），macOS 调用系统 `say`，Linux 调用 `espeak-ng`；三者都实现 `ITtsEngine`，支持直接播报与保存/流式合成。
- **TTS-3 引擎 SPI**：`ITtsEngine.SynthesizeAsync(text, options, ct)` 返回 `IAsyncEnumerable<TtsChunk>`，引擎直接 `yield return` 音频块，消费端天然背压；`ITtsSpeaker` 表示引擎可直接播报，`TtsEngineBase` 统一名称与可用性。
- **TTS-4 选项与结果模型**：`TtsOptions` 携带音色、语速倍率、音量；`TtsChunk` 携带 `AudioFormat` 与 16 位小端 PCM；`TtsResult` 只统计引擎名、格式、字节数、耗时、首包耗时与输出路径。
- **TTS-5 音频输出**：`SaveAsync(path)` 按扩展名推断格式（`.wav`/`.pcm`/`.mp3`/`.flac`）；`SaveAsync(stream, format)` 支持 HTTP/WebSocket 边合成边写；WAV 可 seek 的流回填长度，不可 seek 的流使用流式头；MP3/FLAC 走压缩编码管线（重采样 → 编码 → 容器）。
- **TTS-6 流式 PCM 输出**：`StreamAsync` 逐块产出 16 位小端 PCM 与 `AudioFormat`，供 Web Audio、WebSocket 或自定义协议消费。
- **TTS-7 音色与语速**：`TtsOptions` 提供音色、语速倍率、音量；`GetVoices` 枚举各引擎可用音色；单次调用可覆盖默认选项。
- **TTS-8 文本规范化（可选）**：`Tts.Advanced` 下的 `TtsText` 提供全角转半角、英文整词替换与字母读名、去空白、数字转读法；`ChineseNumber` 提供基数/逐位/年份/小数读法。默认不启用，由需要它的引擎开启。
- **TTS-9 磁盘缓存与预生成（可选）**：`Tts.Advanced` 下的 `TtsCache` 内容哈希命名 + 原子写入 + 最近最少使用淘汰；`TtsPreGenerated` 提前合成固定告警语；通过 `CachedTtsEngine` 装饰器接入，主路径默认不落盘。
- **TTS-10 在线 HTTP 引擎**：请求地址/方法/请求体/请求头全部可配置，解码 WAV、MP3 与裸 PCM，WAV 与裸 PCM 支持边收边写。
- **TTS-11 子进程引擎**：驱动 piper、espeak-ng 等命令行合成器，零原生依赖，标准输出边读边写。
- **TTS-12 兜底与测试引擎**：`NullTtsEngine` 按字长输出静音，保证无语音环境仍有输出，也便于单元测试。
- **TTS-13 压缩音频输出**：输出管线与编码器解耦（见 TTS-23）；MP3/FLAC 已接入 `SaveAsync`（按扩展名分发，走重采样 → 编码 → 容器），并由 CODEC-14 门禁守质量；Opus 待托管 CELT/SILK 完成后再接（网络流式用 Opus、文件分发用 MP3/FLAC）。
- **TTS-14 离线神经模型适配器**：以可选包 `NewLife.Audio.Sherpa` 实现 `ITtsEngine`，基于 sherpa-onnx 支持 VITS / Matcha / Kokoro 常驻加载、逐块流式与模型目录自动发现；核心库不引推理运行时。
- **TTS-15 在线 WebSocket 流式引擎**（待接入）：适配需要长连接与二进制帧协议的在线合成服务。
- **TTS-16 音色目录与多音色管理**：`TtsVoice` 统一携带引擎原生标识 `Id`、语言 `Culture`、性别与适用场景 `Scenarios`，并标记默认音色；`TtsVoiceCatalog` 汇总多个引擎的音色，按语言/性别/场景筛选（`Find`）、按优先级挑选（`Select`：同区域+场景 → 同区域 → 同语种+场景 → 同语种，同档优先默认音色，无匹配返回空而不猜）并写回选项（`Apply`）；云端引擎内置常用音色快照，`TtsClient.GetVoices()` 对云端引擎不再为空，完整列表可按服务商文档替换或追加。
- **TTS-17 阿里云 NLS 引擎**：`AliyunTtsEngine` 支持 AppKey + Token 直连，或 AppKey + AccessKey 由引擎调用 CreateToken 自动换取并缓存令牌；RPC 签名、语速/音量/音调映射、WAV/PCM/MP3 响应解析。
- **TTS-18 腾讯云引擎**：`TencentTtsEngine` 实现 TC3-HMAC-SHA256 签名调用 `TextToVoice`，解析 base64 音频并整段解码为 PCM；音色编号、语速与音量映射。
- **TTS-19 百度引擎**：`BaiduTtsEngine` 用 OAuth 换取并缓存 access_token，以表单提交 `text2audio`；发音人、语速、音量、编码选择。
- **TTS-20 微软 Bing/Azure 引擎**：`AzureTtsEngine` 使用订阅密钥或 Bearer 令牌，按 SSML（音色 + prosody）合成，输出 WAV/MP3；支持自定义区域与输出格式。
- **TTS-21 百度翻译发音（免密钥）**：`BaiduTranslateTtsEngine` 调用翻译网页发音接口，免账号返回 MP3；属非官方接口，生产建议改用 TTS-19。
- **TTS-22 Android/iOS 系统引擎**：Android 走 `TextToSpeech`、iOS 走 `AVSpeechSynthesizer`，与桌面端同属 `ITtsEngine`，随平台目标框架一起提供；离线、免密钥、系统音色。
- **TTS-23 压缩音频输出管线**：把“合成 PCM → 重采样/格式转换 → 编码 → 容器/流式写出”抽成可插拔输出管线，支持背压、取消与首包延迟统计；编码器未达标时在能力查询中如实标注，不静默降级。

> 公共云服务统一继承 `CloudTtsEngine`：复用 HttpClient、统一超时与取消、统一错误读取与 WAV/PCM/MP3 解码；凭证只保存在实例属性中，不写日志、不进异常消息。

## 10. ASR 语音识别（低优先级）

定位为**适配层**，不内置模型、不引推理运行时：本库负责采集、前处理与流式分块，识别由系统能力或可选包提供。优先级低于 TTS，但有明确需求时应能直接接上。

- **ASR-1 识别接口**：`ISpeechRecognizer` 定义流式 PCM 输入与"中间结果 / 最终结果"输出，支持取消与音量事件；可与 VOP 前处理管线（降噪、AGC）直接串联。
- **ASR-2 系统识别适配**：Windows（`System.Speech.Recognition` 反射调用）、Android（`SpeechRecognizer`）、iOS（`SFSpeechRecognizer`），按平台可用性选择。
- **ASR-3 可选离线包**：`NewLife.Audio.Sherpa` 如需提供离线识别，复用同一接口，核心库保持零推理依赖。
- **ASR-4 流式端点与部分结果**：识别接口支持部分结果、最终结果、时间戳、置信度与端点检测；可与 VOP VAD/降噪串联，端点与取消语义明确；离线模型仍由可选包提供。

> 现状：ASR-1~4 全部完成——识别接口、流式端点与部分结果、Windows 系统识别适配、sherpa-onnx 离线包适配均已落地；移动端后端随平台 TFM 补齐。"不做 ASR"的旧结论已改为"低优先级适配层"，理由与边界见[架构设计](架构设计.md) G8。

## 12. 不做什么

明确排除的功能项，避免后续争议。

- **视频编解码**：属于 `NewLife.Video` 或独立视频库的范畴，许音频库介入会模糊边界、膨胀依赖。
- **自研语音识别模型**：ASR 只做适配层（见第 10 节），不训练、不内置声学模型；离线识别由可选包或调用方接入。
- **TTS 模型推理引擎与模型权重**：本库提供 TTS 编排层（极简入口、引擎抽象、系统语音、文件/流式输出、可选缓存与规范化），不内置声学模型与推理运行时。离线神经模型由可选包或调用方以 `ITtsEngine` 适配器接入。
- **深度学习模型训练与推理**：不内置任何 ML 模型，不依赖 ONNX Runtime / PyTorch。如需 ML 能力，由调用方自行集成。
- **音乐制作/DAW 功能**：VST 插件宿主、MIDI 编排、多轨编辑等属于专业音乐制作领域，不在通用音频库范畴。
- **MP3 边角特性**：免费格式（free format）编解码、APEv2/Lyrics3 标签、多封面与同步歌词（SYLT/USLT）不做——现实使用率极低，却会显著膨胀帧解析与标签逻辑。
